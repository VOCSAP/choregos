# Keep-warm plugin: specification

Status: draft, written before any code; O1 to O3 settled with the operator (section 7). Plugin name: `thalpos` (Greek "warmth"). It lives in `plugins/thalpos/` and joins `.claude-plugin/marketplace.json` like `prosopon` and `mitos`.

## 1. Problem

Claude Code's prompt cache for the main conversation expires after one hour without a request (Pro/Max subscription within quota; five minutes otherwise). An operator who steps away for more than an hour pays a full cache write on the next turn of a long session. The goal is to keep the cache warm during a bounded period the operator chooses, at the lowest cost, without polluting the conversation.

## 2. What exists and why it is not enough

- A user skill, `~/.claude/skills/keep-warm-cache/SKILL.md`, already does it with `CronCreate`: a chain of one-shot jobs, each scheduling the next one 55 minutes later and carrying the deadline in its prompt. It works, but every tick is a real turn: tool calls, a reply, the `UserPromptSubmit` hooks of the operator's configuration, and a transcript that grows.
- Two `CronCreate` shapes are known to fail: `*/55 * * * *` fires at :00 then :55 (gaps of 55 and 5 minutes), and a recurring job can fire up to 50 % of its period late (30 minutes at most), which overshoots the one-hour TTL.
- Reference repositories on the same subject:
  - https://github.com/karanb192/cache-tax (MIT) warms with `$.model.fork` after 50 idle minutes inside a bounded window, retries a 429/529/5xx after 1, 2 and 4 minutes while the ping can still land a minute before expiry, and stops when a ping reads nothing or writes at least a tenth of what it reads. One transcript-verified run: a ping at minute 50 read 157k, and a main message at minute 62 read 156,886 tokens from the cache. It is not adopted as is: its cold-send guard has only `refuse` and `warn` modes, it hooks every `prompt.submit`, and it arms at least three hours of warming by itself after a cold write, which contradicts KW1.
  - https://github.com/mupamuc/cache-keepwarm submits a visible service prompt about two minutes before expiry, at most three times in a row, and leaves alone a cache under 20,000 tokens; the TTL (`1h` or `5m`) is an option the user sets.
- thalpos takes cache-tax's warming rules (50-minute period, readback stop, retry) and nothing of its guard.

## 3. Proposed mechanism

- **Warm ping**: `$.model.fork({ prompt })` asks one tool-less question over the session's transcript as the main thread last sent it, same model and system prompt; the API serves that prefix from the prompt cache and the fork adds no turn to the conversation. The reply is discarded.
- **Timer**: re-armed with `$.clock.after` 50 minutes after the latest request of the session (ten minutes of margin leave room for the retries of KW7), that is after each `turn.complete` and after each ping. A session in active use never pings.
- **Activation only on demand**: nothing runs until the operator starts it. Entry point: a slash command registered by the mod (`$.command.register` in `session.start`, answered by a `command.run` hook): `/keep-warm start [hours]`, `/keep-warm stop`, `/keep-warm status` (O1).
- **State**: deadline, last request time, ping count and token usage live in `$.state`, declared in `types/index.d.ts`. A module reload re-arms the timer from `$.state` in `session.start`.
- **Visibility**: `$.ui.status` shows `keep-warm: next HH:MM, until HH:MM` while active, and is cleared on stop.

## 4. Gate L0: measure before building

The whole design rests on one unmeasured claim: a fork refreshes the cache entry of the main thread, with the TTL the main thread uses (one hour). Before any feature code, a probe mod measures it:

1. Note `usage.cache_read_input_tokens` and `cache_creation_input_tokens` of a fork right after a main turn.
2. Wait more than five minutes but less than one hour, fork again: the read must still cover the prefix.
3. Fork at 50 minutes after the last main turn (C), then fork again 55 minutes after C (E), when neither the main entry's hour nor a five-minute entry of the earlier forks can explain a read: E must read the prefix. One minute after E, a main turn submitted by the probe must read the prefix too, which shows the main thread and the fork share the entry.
4. The probe restarts its schedule on any main turn before E, so only an undisturbed stretch counts.

If step 3 fails, the fork does not extend the main entry. The fallback is `$.prompt.submit` with a minimal prompt, which starts a visible turn; the spec is then revised before building.

## 5. Requirements

Each requirement gets a stable identifier and a `claude plugin test` case, as in `CONTRACT.md`. The clock is mocked (`mock.clock`).

- **KW1**: no timer, no fork and no status line exist before `/keep-warm start`.
- **KW2**: `start` without a duration means 3 hours; `start <h>` takes a positive number of hours (`5`, `5h`, `1.5h`); a duration under one hour, non-positive, unreadable or above the `max_hours` option (default 12) is refused with the usage line and changes nothing.
- **KW3**: `start` while active replaces the deadline with now plus the new duration and keeps the time of the next ping or retry; it never stacks a second timer.
- **KW4**: a ping happens only when 50 minutes have passed since the latest request of the session (main turn or ping); each `turn.complete` re-arms the timer. `start` counts from the latest request seen (main turn or ping), not from the command, and waits for the next turn when that request is already 59 minutes old.
- **KW5**: no ping is sent at or after the deadline; on reaching it, the timer is cancelled, the status line cleared, and one toast says the period ended.
- **KW6**: `stop` cancels the timer, clears the status line and keeps no deadline; `stop` while inactive answers that nothing was active.
- **KW7**: a ping that answers but reads nothing, or writes at least a tenth of what it reads, means the cache was cold: the plugin stops as in KW6 and says why in one toast. An `api-error` with status 429, 529 or 5xx is retried after 1, 2 then 4 minutes, as long as the retry lands before the deadline and before the 59th minute since the latest request; any other failure, or a retry that cannot land in time, stops as in KW6 with one toast. `nothing-to-fork` (no turn yet, or right after `/clear`) sends nothing, stops nothing, and waits for the next `turn.complete` to re-arm.
- **KW8**: `status` gives the deadline, the next ping time, the ping count and the summed `cache_read_input_tokens` / `cache_creation_input_tokens` of the pings.
- **KW9**: a module reload during an active period keeps the deadline and re-arms the timer from `$.state`; a reload after the deadline starts nothing.
- **KW10**: the plugin makes no network, file or process access other than `$.model.fork`, and writes nothing to the transcript.

## 6. Out of scope

- Keeping the cache of subagents or of other sessions warm.
- Any durable schedule across Claude Code restarts.
- Choosing the ping interval by measurement of the TTL in use: 50 minutes is fixed.
- A guard on a cold send, as cache-tax has.

## 7. Settled questions

- **O1**: the entry point is the mod's slash command; no skill and no model-callable tool.
- **O2**: the plugin is named `thalpos`.
- **O3**: the session cannot read its TTL (`cache_ttl` only rides the `PostModelSwitch` hook input), so thalpos assumes one hour and takes no TTL option. In a five-minute session the first ping reads nothing and KW7 stops the plugin; the README tells API-key users to set `promptCacheTtl` to `"1h"`.
